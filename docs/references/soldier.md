# `Soldier` shape reference

A Soldier is the persistent identity unit in the game — what lives in `Game.roster[]`. Constructed exclusively via `createSoldier(opts)` at `js/roster.js:92`. Persisted under `cr_s<slot>_cr_roster`. **No equipment fields** live on this object (per [ADR-0004](../decisions/ADR-0004-armory-single-source-of-truth.md)) — gear ownership lives in `armory.items` (via `assignedTo` + `equipped`) and `armory.kits[soldier.id]`.

## Object construction sites

Every place a Soldier gets created. Useful when chasing "field X is missing in newly-created soldiers."

| Path | Where | What |
|---|---|---|
| `createSoldier(opts)` | `roster.js:92` | **The only constructor.** Every Soldier comes from here |
| `generateRecruit(pool, role)` | `roster.js:158` | Wraps `createSoldier` with E-1 defaults + low personality; calls `equipSoldierStandardIssue` |
| `launchMission('firstTime')` hero | `mission.js:48` | Creates the player-character hero (`isPlayerCharacter: true`) + calls `equipSoldierStandardIssue` |
| `generateMissionReinforcements` | `mission.js:190` | Creates 5 reinforcements per call (3 infantry + 2 vehicle crew); each gets `equipSoldierStandardIssue` |
| `seedStarterRoster` | `roster.js:1463` | Seeds 45 starter soldiers (21 vehicle crew + 24 infantry). Only fires from `storage.load()`, **not** from first-mission flow. Infantry get `equipSoldierStandardIssue`; vehicle crew don't |

## Invariants

- **`id` uniqueness**: globally unique within a save slot. `generateId()` produces `sol_<base36 timestamp>_<base36 counter>` (`roster.js:42`). Counter is module-scoped — survives within a session but not across module reloads
- **`status` enum**: `'active' | 'wounded' | 'kia' | 'retired'`. No other values valid
- **`pool` enum**: `'infantry' | 'vehicle' | 'officer'`. Drives rank table choice
- **`rankIndex` bounds**: `[0, RANK_TABLE.length - 1]` for infantry/vehicle pools, `[0, OFFICER_RANKS.length - 1]` for officer pool
- **`personality.*`**: clamped to `[0, 1]` by `clamp01()` in constructor
- **`physicals.*`**: bounded to `[0, 100]`. Migration enforces via `Math.min/max`
- **`training[role]`**: bounded to `[0, TRAINING_CAP]` where `TRAINING_CAP = 1.0`
- **`mmr` floor**: `getMMR(soldier)` returns `max(mmr, mmrFloor)`. The two-field design lets the floor ratchet up via commendations while `mmr` can fluctuate
- **Vehicle assignment pairing**: `assignedVehicleId` and `assignedSlot` are both null OR both set. Enforced by `assignToVehicle` / `unassignFromVehicle` helpers
- **Commendations are append-only**: `commendations[]` never shrinks. Each award also raises `mmrFloor` permanently
- **No equipment fields**: `soldier.loadout` and `soldier.kits` MUST NOT exist on the soldier object. Query armory instead

## Persistence

- **Saved by**: `saveRoster()` at `roster.js:1641`. Writes the full roster array to `localStorage[cr_s<slot>_cr_roster]`. Also POSTs to `/api/debug/roster` for the server-side debug snapshot
- **Loaded by**: `loadRoster()` → `importRoster(data)` → `_migrateRoster()` (`roster.js:1572`)
- **Storage key**: `cr_s<slot>_cr_roster` (slot-prefixed via `_slotKey`)
- **Migrations**:
  - `_migrateRoster` (`roster.js:1572`) — non-destructive backfill for physicals / mos / training. Runs on every `loadRoster()`. Idempotent
  - `_migrateToArmorySOT` (`storage.js`) — one-shot, gated by `armory._sotMigratedV1`. Moves `soldier.kits` → `armory.kits[soldier.id]` and strips both `loadout` and `kits` fields. See [ADR-0004](../decisions/ADR-0004-armory-single-source-of-truth.md)

## Gotchas

- **`soldier.loadout` / `soldier.kits` are gone** ([ADR-0004](../decisions/ADR-0004-armory-single-source-of-truth.md)) — never add them back. The migration that strips them is permanent; downgrade would re-trigger duplication
- **`createSoldier` is the only constructor** — any new fields should be added there to keep the construction sites converging. Don't pre-initialize equipment fields (the entire point of ADR-0004)
- **`seedStarterRoster` is a near-dead path** — it only fires when `load()` runs on a slot with empty roster, which doesn't happen on the user-facing first-mission flow (`launchFirstTimeMission` bypasses `load()` entirely). Real first-mission soldiers come from `launchMission` + `generateMissionReinforcements`
- **`isPlayerCharacter` is one-way** — set once at hero creation, only read to block retirement. Don't toggle
- **`assignedVehicleId` cleanup on vehicle delete** — `roster.js:1739/1757` clears stale crew assignments on load. Don't leak vehicle IDs in roster after a vehicle is removed
- **Reserved / unused fields**: `bonds`, `missionsWithVehicle`, `vehicleExpertise`, `isSquadLeader`, `callsign`, `name.nickname` are initialized but have no current write or read sites. Future work
- **`status: 'retired'` removes from roster** but preserves the soldier object in `recentFallen` / `memorial` — that's how memorial lineage works. Don't assume "retired" means "deleted"
- **`mmr` post-battle adjustment is in `progression.js`**, not `roster.js`. The roster-side `recordBattleScore` writes the final value; the actual delta calculation happens upstream
